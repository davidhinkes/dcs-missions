# Mission rework review — 2026-11-05

This review combines the conversation, Git history and mission verification/lessons records. Earlier flight problems are documented reports, not independently reproduced diagnoses. Later drone faults include confirmed mock fault injection. Design refinements are distinguished from implementation defects.

## Workflow to use next time

1. Write a one-page mission contract: player role and distinctive mechanic, SP/MP scope, modules, start/base roles, route/duration, loadout/fuel assumptions, information rules and success/retry/failure conditions. Describe the player experience in plain language.
2. Define support contracts and full menu paths. Automatic travel and manual tactical clearance are separate choices. Include arrival/loss reports, fallback behavior and realistic transit estimates.
3. Build the smallest playable slice first: intended slot, safe departure, one objective interaction and recovery. Prefer an inspected site over elaborate procedural placement until the basic sortie works.
4. Run portable build/archive checks and meaningful mocked failure/boundary tests. Label skipped native checks explicitly. Confirm the actual delivered archive embeds the current scripts.
5. Conduct staged DCS checks: (a) start/terrain/servicing/loadout; (b) the distinctive AI/sensor mechanic, such as remote lasing; (c) one complete normal sortie; (d) relevant abort/retry/failure case. If simulator access is unavailable, document the gap and supply the checklist; independent coding can continue, but additional features do not erase the validation debt.
6. Add complexity incrementally. Changes to starts, geography, aircraft count or support timing trigger review of dependent logic, briefing facts and native checks.
7. Deliver the tested artifact/revision with actual installation status. Back up manual editor changes, verify a real deployment when available, and remind the user to restart the mission. A push to GitHub is not installation on the DCS PC.

## What is implemented versus proposed

Current missions have specific mock checks for many of these cases, including simplified menus and Open Door optional-drone failure isolation. These checks do not automatically transfer to a new mission. This document and the expanded design template are process guidance, not a new validator or CI pipeline. Native drone orbit/remote Hellfire acquisition and complete latest-revision sorties remain unverified in the recorded evidence.

The proposed scripted copilot observer has only been discussed. It is not implemented, native crew AI, or multiplayer validation. Before building it, settle detection/disclosure rules and SP/MP scope; multiplayer requires per-group delivery, client lifecycle handling and mission-trigger review.
